# 设计文档

## 目标与非目标

**目标**：一个能上线跑的企业知识库问答服务，且检索链路的每个选型都有评测数据支撑。

**非目标**：不做通用 RAG 框架，不做多租户 SaaS，不做模型训练。索引实现是教学级、可替换的，
不是要和 Milvus 比性能。

## 数据流

**写入路径（离线）**：文档 → 加载与标题抽取 → 切分（recursive，块长 400 / 重叠 80）
→ 向量化 → 建 BM25 倒排索引 → 落盘（`chunks.jsonl` + `vectors.npy` + `meta.json`）。

**查询路径（在线）**：问题 → 改写（多轮指代补全）→ 双路召回（各 20 条候选）
→ RRF 融合 → 启发式重排 → 置信度门控 → Prompt 组装（强制引用编号）
→ 生成（失败则降级为抽取式）→ 引用解析 → 缓存 → 返回。

## 关键决策

### ADR-1 自己实现 BM25 与向量索引

- **背景**：需要用消融证明每个检索组件的贡献，如果检索行为藏在外部服务里，无法解释分数从哪来。
- **选择**：`index.py` 内实现 Okapi BM25（带倒排索引）与扁平余弦索引。
- **替代方案**：Elasticsearch / Milvus / rank_bm25 库。
- **代价**：扁平索引是 O(N) 扫描，语料上万片段后必须换 ANN 索引；换来的是全链路可解释、零外部依赖。

### ADR-2 中文用字符 bigram，不引分词器

- **背景**：评测结论必须可复现，而分词器版本升级会改变切分结果，进而改变所有指标。
- **选择**：中文按字符 bigram 切分，英文数字按词切分，检索与索引共用同一套逻辑。
- **替代方案**：jieba、按标点切分、字级 unigram。
- **代价**：bigram 会引入一些无意义组合，索引体积比词级更大；换来的是无未登录词问题、结果稳定。

### ADR-3 融合用 RRF 而不是分数加权

- **背景**：BM25 分值是量纲不确定的实数，向量余弦在 [-1,1]，两者尺度不可比。
- **选择**：只用排名的 RRF，并对权重做了消融（见 `eval/report.md`）。
- **替代方案**：Min-Max 归一化后加权求和、按 z-score 标准化。
- **代价**：RRF 丢掉了分数的绝对信息，无法区分"两路都强烈命中"和"两路都勉强命中"；
  换来的是对不同检索器的分数量纲免疫，换组件时无需重新调归一化参数。

### ADR-4 重排用启发式，不默认上交叉编码器

- **背景**：目标场景要能在没有 GPU 的机器上跑起来，并且重排逻辑要能解释给面试官/同事。
- **选择**：idf 加权查询覆盖率 + 最长公共子串比例 + 标题命中 + 原始融合分，线性组合。
- **替代方案**：bge-reranker 等交叉编码器。
- **代价**：精度低于交叉编码器（这也是"重排对强分支增益有限"的原因之一）；
  `CrossEncoderReranker` 已实现接口，装依赖即可替换。
- **实测修正**：换成真实语义向量后，这个重排器在纯向量上把 R@1 从 0.929 拉到 0.905（负收益）。
  它补的是"稠密分支弱"这个洞，洞被填上之后，纯词法的重排就只剩副作用了 —— 见 README「换成真实语义向量之后」。

### ADR-5 置信度门控用多片段并集，而不是最佳单片段

- **背景**：拒答判据直接决定误答率与漏答率，最初用"最佳片段的词覆盖率"，多跳问题大量被误判为无依据。
- **选择**：取前 3 个片段词项的并集计算 idf 加权覆盖率。
- **实测**：相同误答率下，并集定义的漏答率显著更低（例如误答率为 0 时，漏答率 0.286 vs 0.548）。
- **代价**：并集更宽松，误答率相应上升，必须靠阈值重新平衡。

### ADR-6 默认用离线确定性向量

- **背景**：作品集项目若要求 API Key 才能跑，等于没有人能在本地验证那些数字。
- **选择**：默认 signed hashing 向量，4096 维，行为完全确定。
- **替代方案**：sentence-transformers（本地语义模型）、OpenAI embeddings。
- **代价**：它是词法向量，不理解同义词，所以本仓库的混合检索结论只在词法设定下成立。

### ADR-7 配置走环境变量

- **选择**：`AppConfig.from_env()`，不引 YAML 解析依赖。
- **代价**：嵌套配置表达力弱；换来容器与 CI 覆盖参数时不用挂载配置文件。

### ADR-8 引用格式在解析层归一化

- **背景**：接上真实模型后，小模型会把提示词里的占位符原样抄下来，把引用写成
  `[编号1]`、`【编号：2】`，也会把多个编号挤成一格 `[1、2]`。
- **选择**：两头都做 —— 提示词里给具体示例（`[1]`、`[2]`），解析层再用
  `service.normalize_citations()` 归一化成 `[数字]`，解析与前端高亮只认这一种格式。
- **替代方案**：只改提示词（弱模型不保证遵守）；只做解析归一化（放掉了提示词里最便宜的那次修正）。
- **代价**：解析层多一层正则，且会改写答案原文。换来的是这类失败不再静默 —— 它不抛异常，
  只会让引用高亮和引用准确率一起悄悄变成 0，比答案答错更难发现。

## 扩展点

| 想换什么 | 改哪里 | 接口约束 |
| --- | --- | --- |

## 性能与容量

- 索引规模：54 个片段时检索耗时约 1~2 ms（单机、纯 Python + numpy）。
- 瓶颈：向量检索是 O(N) 全量内积，BM25 有倒排索引。片段数上万后向量侧需要换 HNSW / IVF。
- 并发：服务本身无状态（索引只读），可直接多 worker；`uvicorn --workers` 或容器横向扩。
- 缓存：LRU 512 条，键包含检索参数与对话历史签名，避免多轮串答案。

## 已知问题

1. `parent_child` 切分把父块也放进索引，会和子块竞争候选位，尚未做去重或加权。
2. 启发式改写只看"问题是否过短或含指代词"，没有判断上一轮是否真的相关，可能引入错误语境。
3. 置信度是词法信号，对"用同义词提问"的场景偏保守，会误判为无依据。
4. 成本估算用的是硬编码单价表，只适用于量级判断，接真实网关后应改为读返回的计费字段。
5. 评测集没有划分 dev/test，超参选择与报告使用同一批数据，方法学上有乐观偏差（已在报告里注明）。
6. 置信度阈值依赖语料自身的 idf 分布，换语料后必须重新标定；小语料上 idf 统计不稳定，
   门控会过度拒答（单测因此显式关闭门控）。更稳的做法是改成与语料规模无关的相对判据。
7. 抽取式 stub 挑句子靠 bigram 重合度，会被跨词边界的噪声组合误导：问"混合检索是怎么融合的"，
   `合的`（切自"混合的"）和 `混合` 在一句无关的批处理描述里同时命中，得分反超真正讲 RRF 的句子。
   实测这套冲突不能靠 idf 修——语料里噪声组合 `合的` 的 idf（2.76）反而高于内容词 `检索`（0.94），
   因为噪声组合本身就很罕见。要根治得引入分词或词关联度（凝固度 / PMI），与 ADR-2 的可复现诉求冲突，
   所以这里只记录现象，真实模型不经过这条路径。
