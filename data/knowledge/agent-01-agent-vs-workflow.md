# Agent 与工作流的边界

## 什么时候不该用 Agent

如果任务的步骤是确定的、可以提前画出来的，就应该写成工作流而不是 Agent。工作流是代码控制流程，每一步的输入输出、失败处理、超时都是显式的；Agent 是把决策权交给模型，让它自己决定下一步调什么工具。后者的优势是能处理事先没预料到的分支，代价是不确定性、更高的 token 消耗和更难排查的故障。

## 判断标准

可以用三条标准判断：步骤数量是否固定、分支是否可穷举、错误的代价是否可接受。三条都满足时用工作流。典型适合 Agent 的场景是开放式调研、需要多轮试探的工具调用；典型不适合的是固定表单填写、确定性的数据同步。

## 混合架构

生产系统里更常见的是混合架构：外层用工作流控制主干流程，把需要判断的局部节点交给模型决策。这样既有确定性又不失灵活性，而且故障范围被限制在局部，不会出现整条链路失控的情况。
